# Quasar 项目开发规范

> 本规范约束 Quasar 项目中功能与模块从设计到交付的完整开发流程，覆盖测试、文档、审查、验收等环节，是对 `COMMIT_CONVENTION.md`（提交规范）和 `CODING_CONVENTION.md`（编码规范）的上层补充。
>
> 三者关系：开发规范定义"做什么、何时做"，编码规范定义"怎么写"，提交规范定义"怎么记"。

---

## 1. 开发工作流

### 1.1 开发前

开发任何功能或模块前，必须完成以下步骤：

| 步骤 | 内容 | 输出物 |
|------|------|--------|
| 1. 需求确认 | 阅读**设计规格文档**（描述功能范围、端点定义、请求/响应格式、错误码的文档）对应章节 | 明确的验收标准 |
| 2. 设计对齐 | 如涉及数据模型变更，阅读**数据模型文档**，确认是否需要修改 DDL 或 trait 签名 | 变更清单 |
| 3. 任务拆分 | 将功能拆分为独立子任务（如 trait 定义 → 存储实现 → 端点实现 → 测试 → 文档） | 提交计划（大致的 commit 顺序） |

**反例：** 不读设计文档直接开写，结果端点路径与规范不符、错误码映射错误，返工重写。

### 1.2 开发中

按以下顺序实现，每个步骤至少一次 commit：

1. **契约层**：更新 `core` crate 中的数据结构、trait 定义、错误枚举
2. **实现层**：在 `storage` 或 `adapter` 中实现契约
3. **验证层**：编写测试，确保功能正确
4. **文档层**：更新 Rust doc、设计文档（如数据模型变更）

**提交粒度原则：**

- 每个 commit 只做一件事（对应单一 type/scope）
- trait 定义变更和存储实现变更分开提交，便于 review 时聚焦
- 测试代码可以和被测代码放在同一 commit，但不得跨功能混合

### 1.3 开发后

| 检查项 | 方法 |
|--------|------|
| 编译通过 | `cargo build` |
| 测试通过 | `cargo test` |
| Lint 通过 | `cargo clippy -- -D warnings` |
| 格式化 | `cargo fmt` |
| 文档生成 | `cargo doc`（检查是否有文档警告） |

全部通过后，方可发起 PR。

## 2. 测试规范

### 2.1 测试分类与选择标准

Rust 提供三种内置测试类型，Quasar 根据场景选择：

| 测试类型 | 位置 | 适用场景 | 必须/视情况 |
|----------|------|----------|-------------|
| **单元测试** | `#[cfg(test)] mod tests`（模块内） | 纯逻辑函数、错误分支、边界条件、工具函数 | **必须** |
| **集成测试** | `tests/` 目录 | 端点完整请求/响应链路、跨组件协作、数据库交互 | **必须** |
| **文档测试** | `///` 中的代码示例 | 公共 API 的使用示例（编译验证） | 视情况 |

**选择原则：**

- 纯逻辑（如数据转换、校验规则）→ 单元测试
- 涉及数据库操作、HTTP 请求处理 → 集成测试
- 复杂公共 API（如 builder pattern）→ 可考虑文档测试作为补充示例

### 2.2 单元测试规范

```rust
#[cfg(test)]
mod tests {
    use super::*;

    // 测试命名：test_被测函数_场景_预期结果
    #[test]
    fn test_parse_namespace_valid() {
        let input = "db.schema";
        let result = Namespace::parse(input).unwrap();
        assert_eq!(result.levels(), vec!["db", "schema"]);
    }

    #[test]
    fn test_parse_namespace_empty_returns_error() {
        let result = Namespace::parse("");
        assert!(matches!(result, Err(StoreError::InvalidInput(_))));
    }
}
```

**要求：**

- 测试命名清晰：`test_{function}_{scenario}_{expected}`
- 每个测试只验证一个行为点
- 使用 `assert!`、`assert_eq!`、`assert_ne!`、`assert_matches!`（Rust 1.77+），避免裸 `unwrap()` 做断言
- 对异步函数使用 `#[tokio::test]`

### 2.3 集成测试规范

```
quasar-server/
├── src/
└── tests/
    ├── common/
    │   └── mod.rs          # 共享的测试辅助（启动测试服务器、数据库清理）
    ├── lance_namespace.rs   # Lance Namespace 端点测试
    ├── lance_table.rs       # Lance Table 端点测试
    ├── iceberg_namespace.rs # Iceberg Namespace 端点测试
    └── iceberg_table.rs     # Iceberg Table 端点测试
```

**要求：**

- 每个端点文件对应一组集成测试
- 测试覆盖：成功路径 + 主要错误路径（404、409、400 等）
- 并发安全：集成测试共享数据库时，使用唯一标识（如 `uuid::Uuid::new_v4()`）避免数据冲突
- 测试清理：每个测试完成后清理自身创建的数据，或在 `common` 中提供 `setup_test_db` 函数创建隔离 schema

**最小集成测试集：**

| 场景 | 必须覆盖 |
|------|----------|
| CRUD 端点 | Create → Read → Update → Delete 完整链路 |
| 冲突处理 | 重复创建返回 409、不存在时删除返回 404 |
| 参数校验 | 非法输入返回 400 |
| 列表查询 | 空列表、分页、过滤条件 |

### 2.4 测试用例设计原则

编写测试前，先列出被测功能的"行为点"（behavior points）：

```
函数：create_namespace
行为点：
  1. 正常创建 → 返回 201，数据持久化
  2. 同名同 format 已存在 → 返回 409
  3. 参数校验失败（如空名）→ 返回 400
  4. 数据库连接失败 → 返回 500
```

每个行为点至少对应一个测试用例。错误路径的测试和成功路径同等重要。

### 2.5 测试覆盖率

不做硬性百分比要求，但遵循以下原则：

- **核心逻辑**（`core` crate 中的模型方法、校验逻辑）：必须全覆盖
- **存储层**（`storage` crate）：每个 `CatalogStore` trait 方法至少一个集成测试
- **适配器层**（`adapter` crate）：每个端点 handler 至少一个集成测试（成功 + 主要错误）
- **工具脚本**：如有 CLI 工具或辅助脚本，需配套单元测试

## 3. 文档规范

### 3.1 文档分类与选择标准

| 文档类型 | 位置 | 内容 | 何时编写/更新 |
|----------|------|------|---------------|
| **Rust API 文档** | `///` 注释 | 公共 API 的用途、参数、返回值、错误 | 编写公共 API 时同步编写 |
| **设计文档** | `docs/mvp/*.md` | 数据模型、架构设计、端点规格 | 设计阶段编写；实现阶段如有偏差需同步更新 |
| **模块注释** | `//!` 注释 | crate/模块级别的概述 | 创建新 crate 或模块时编写 |
| **CHANGELOG** | `CHANGELOG.md` | 版本变更摘要 | 版本发布时编写 |
| **README** | `README.md` | 项目简介、快速开始、架构概览 | 项目初始化时编写；重大变更时更新 |

### 3.2 Rust API 文档要求

**所有 `pub` 项必须有文档注释**，具体要求如下：

```rust
/// 根据名称和格式创建 Namespace。
///
/// 如果已存在同名同 format 的 Namespace，返回 [`StoreError::AlreadyExists`]。
///
/// # 参数
///
/// - `name`: Namespace 名称，不允许为空
/// - `format`: 资产格式（Lance 或 Iceberg）
/// - `properties`: 可选的附加属性
///
/// # 示例
///
/// ```
/// use quasar_core::{Namespace, AssetFormat};
///
/// let ns = Namespace::new("prod", AssetFormat::Lance, None);
/// ```
pub fn new(
    name: &str,
    format: AssetFormat,
    properties: Option<serde_json::Value>,
) -> Result<Self, StoreError> {
    // ...
}
```

**结构要求：**

- 第一行：一句话摘要（显示在 rustdoc 列表页）
- 空行后：详细说明
- `# 参数`：每个参数的含义和约束
- `# 返回值`：返回值说明（如非 `Result` 可省略）
- `# 错误`：可能返回的错误及触发条件
- `# 示例`：简单使用示例（复杂场景可省略）

**trait 文档额外要求：**

```rust
/// 目录存储抽象。
///
/// 定义了 Namespace、Asset、AssetVersion 的持久化操作。
/// 具体实现由 `quasar-storage` crate 提供。
///
/// # 实现注意
///
/// 实现者需保证 `create_namespace` 的幂等性：同名同 format 已存在时应返回
/// `StoreError::AlreadyExists`。
pub trait CatalogStore {
    // ...
}
```

### 3.3 设计文档同步要求

当实现与设计文档出现偏差时，**优先修正设计文档**，而非事后补记。

| 变更类型 | 需更新的文档 | 说明 |
|----------|-------------|------|
| 数据模型字段增减 | **数据模型文档** | 同步更新 Rust struct 定义和 PostgreSQL DDL |
| trait 方法签名变更 | **数据模型文档** | 更新 trait 定义和使用说明 |
| 端点路径/请求/响应变更 | **设计规格文档** | 更新对应协议的端点规格表 |
| 错误码映射变更 | **设计规格文档** | 更新错误码对照表 |
| 新增 crate/模块 | **架构文档** | 更新 crate 分层图和说明 |

**更新格式：** 在文档末尾的"修订记录"中追加条目，包含：
- 版本号（按语义增长）
- 变更摘要
- 变更原因（简要）

### 3.4 代码内注释规范

仅在以下场景添加注释：

- **非显而易见的约束**：如特定 SQL 语句的优化原因
- **临时性方案**：标注 `// TODO:` 或 `// FIXME:`，说明原因和计划修复时间
- **协议对齐说明**：说明某段代码对应上游规范的哪个章节

**禁止：** 注释重复代码本身已表达的信息。

```rust
// ✅ 说明为什么这么做
// Iceberg REST 规范要求 404 时返回空对象而非错误，见规范 §5.2.1
let response = if result.is_none() {
    Json(json!({}))
} else {
    Json(serde_json::to_value(result).unwrap())
};

// ❌ 重复代码含义
// 创建 namespace
let ns = create_namespace(&name).await?;
```

## 4. 代码审查规范

### 4.1 PR 前自查清单

发起 PR 前，作者必须确认以下事项：

```markdown
## 自查清单

- [ ] 代码编译通过 (`cargo build`)
- [ ] 测试通过 (`cargo test`)
- [ ] Clippy 无警告 (`cargo clippy -- -D warnings`)
- [ ] 已格式化 (`cargo fmt`)
- [ ] 文档生成无警告 (`cargo doc`)
- [ ] 新增/修改的公共 API 已写文档注释
- [ ] 单元测试覆盖新增逻辑
- [ ] 集成测试覆盖新增端点（如适用）
- [ ] 设计文档已同步更新（如数据模型/端点有变更）
- [ ] Commit message 符合规范
```

### 4.2 PR 描述模板

```markdown
## 变更摘要

一句话描述本次 PR 的核心变更。

## 变更类型

- [ ] feat: 新功能
- [ ] fix: Bug 修复
- [ ] refactor: 重构
- [ ] docs: 文档更新
- [ ] test: 测试相关
- [ ] chore: 杂项

## 影响范围

- 涉及的 crate：`core` / `storage` / `adapter` / `server`
- 涉及的模块/端点：

## 主要变更

1. 变更点 1（简要说明 + 原因）
2. 变更点 2

## 测试覆盖

- 新增单元测试：X 个
- 新增集成测试：X 个
- 手动验证场景：

## 设计文档更新

- [ ] 无需更新
- [ ] 已更新**数据模型文档**（版本号：V x.x）
- [ ] 已更新**设计规格文档**（版本号：V x.x）

## 破坏性变更

- [ ] 无
- [ ] 有（说明迁移方式）
```

### 4.3 审查者检查项

审查者 focus 的优先级：

| 优先级 | 检查项 | 说明 |
|--------|--------|------|
| P0 | 正确性 | 逻辑是否正确、错误处理是否完备、并发安全 |
| P0 | 规范遵循 | 是否符合编码规范、提交规范 |
| P1 | 测试质量 | 测试是否覆盖主要场景、测试是否可靠（非 flaky） |
| P1 | 文档同步 | 公共 API 是否有文档、设计文档是否同步 |
| P2 | 代码简洁 | 是否有更简洁的实现、是否有重复代码 |
| P2 | 性能 | 是否有明显的性能问题（如 N+1 查询） |

**审查响应时间：**

- 非紧急 PR：24 小时内给出首次反馈
- 紧急修复（hotfix）：2 小时内响应

### 4.4 合并标准

PR 必须满足以下条件方可合并：

1. 至少一名审查者批准（Approve）
2. CI 全部通过（编译、测试、clippy、格式化）
3. 作者已回应所有审查意见（解决或说明不采纳的理由）
4. 无待解决的冲突

## 5. 设计变更规范

### 5.1 什么情况下需要走设计变更流程

| 变更类型 | 处理方式 |
|----------|----------|
| 新增端点（已有协议内） | 直接在 PR 中说明，无需单独设计评审 |
| 新增协议适配器（如新增 Delta Lake） | 需先补充设计文档，再走 PR |
| 数据模型字段增减 | 需更新**数据模型文档**，PR 中说明 |
| trait 签名变更 | 需更新**数据模型文档**，PR 中说明影响范围 |
| 存储层实现切换（如 PostgreSQL → MySQL） | 需先补充设计文档 |
| 架构层级调整 | 需评审**架构文档**后实施 |

### 5.2 变更流程

1. **识别影响**：变更是否涉及数据模型、trait 契约、端点语义
2. **更新设计文档**：如需要，先修改对应设计文档，在修订记录中追加条目
3. **实现与测试**：按本规范"开发工作流"执行
4. **PR 审查**：审查者重点检查设计文档与实现的一致性

## 6. 阶段验收标准

每个开发阶段（S0 ~ S10）完成后，须满足以下标准方可标记为"已完成"：

| 验收项 | 标准 |
|--------|------|
| 功能实现 | 阶段内所有端点/功能已实现并通过手动验证 |
| 单元测试 | 新增核心逻辑有单元测试覆盖 |
| 集成测试 | 新增端点有集成测试覆盖（成功 + 错误路径） |
| 编译检查 | `cargo build`、`cargo clippy -- -D warnings` 通过 |
| 文档 | 新增公共 API 有文档注释；设计文档已同步（如有变更） |
| 进度更新 | **进度跟踪文档**中该阶段状态标记为"已完成" |

**标记完成后**，从 `dev` 发起 PR 合并到 `main`，按 `COMMIT_CONVENTION.md` 中的分支策略执行。
